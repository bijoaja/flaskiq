# CI — Design Spec (flaskiq)

Date: 2026-10-27
Status: Draft, awaiting approval (no implementation yet)

## 1. Background

flaskiq is a template that `pyartisan new flask` clones. It has no CI, no tests, and no `.github/`
folder. Facts that shape the design:

- `requirements.txt` has 20 lines, mostly exact pins. A pin that lacks a wheel for a new Python
  broke installs once already: `psycopg2-binary==2.9.10` had no wheel for Python 3.14 and failed
  (issue #1, fixed by PR #4 with 2.9.13). Nothing would have caught that before a user did.
- On `main`, `import app` fails (stale imports in `app/service/__init__.py`; see the test-structure
  spec). A CI import check would have caught this.
- The Dockerfiles use `python:3.12-slim`. Python 3.14 was verified only by installing the requirements and importing `psycopg2` and the Flask extensions.
- The repo is public, default branch `main`.

## 2. Goals

- Every PR is checked automatically; `main` is checked again after each merge.
- The pinned requirements install on the Python versions the template claims to support.
- The app can be imported and, once tests exist, the tests pass.
- A user who clones the template gets one that at least installs and imports.

## 3. Non-goals and anti-goals

Non-goals: Docker image builds, deployment, lint or format, coverage thresholds, testing the AI
services, dependency-update bots.

Anti-goals: loosening a pin or dropping a Python version only to get green; a workflow that needs
secrets, a running Postgres, Redis, or Ollama; a check that passes while `import app` is broken.

## 4. Decisions

Made by the user:
- One workflow per repo, on pull requests and pushes to `main`.
- `.github/workflows/ci.yml` is allowed to ship into projects created by `pyartisan new flask`, because that command clones the template unchanged. No exclusion mechanism is built.
- Specs live in this repo's `docs/superpowers/specs/`.

My calls (the user can overrule any of them):
- Matrix: `ubuntu-latest` x Python `3.12` (the Docker version) and `3.14` (the version that exposed
  the psycopg2 problem). Linux only, because the template runs in Linux containers.
- One workflow PR, added **after** the import fix and the test suite are merged (order in section 7).
  Before that, `import app` is broken and there is nothing to run, so an earlier workflow would be red
  on its own PR. The `check` job installs `requirements-dev.txt`, runs `python -c "import app"` with
  `DATABASE_URL=sqlite://` and fixed `SECRET_KEY`/`JWT_KEY`, then runs `pytest`. The import step stays
  separate so an import failure is reported on its own line instead of as a pytest collection error.
- Naming is the same in all three repos: the file is `.github/workflows/ci.yml`, the workflow `name:`
  is `ci`, and the aggregate job is `ci-ok`. Copy these; do not invent new ones.
- The Python 3.14 cell is **required**. If it fails, the cause is fixed first (a pin bump in its own
  issue and PR), because dropping 3.14 or letting it fail softly is an anti-goal.
- Aggregate job `ci-ok` that `needs` the matrix job, so the ruleset requires one stable name.
- Triggers `pull_request`, `push` on `main`, `workflow_dispatch`; `permissions: contents: read`; a
  `concurrency` group per ref cancelling older runs.
- Pip cache keyed on `requirements*.txt` (via `actions/setup-python` cache) to keep runs short; the
  `langchain`/`openai` packages are large.

## 5. Jobs

| Job | Runs on | What it does |
|---|---|---|
| `check` | matrix: Python 3.12, 3.14 | checkout, set Python, `pip install -r requirements-dev.txt`, import check, `pytest` |
| `ci-ok` | `ubuntu-latest` | `needs: [check]`, `if: always()`, fails unless `check` succeeded |

Environment for the job: `DATABASE_URL=sqlite://`, `SECRET_KEY` and `JWT_KEY` set to fixed non-secret values. The check must not read `.env`.

## 6. Making the check mandatory

Same as the other repos: a workflow alone does not block merging. The owner creates a ruleset on `main` (require a PR, require the status check `ci-ok`, decide on admin bypass) in the GitHub UI, after the workflow has run once and is green. Claude does not change repository settings. A direct push to `main` still triggers CI, but only after the code is in.

## 7. Risks

- **Order of work:** (1) the import-fix PR, (2) the test PR, (3) the workflow PR, which triggers
  itself and must be green, (4) a README mention of CI, (5) the owner creates the ruleset in the
  GitHub UI. Doing 3 before 1 and 2 makes the workflow PR red on its own check.
- Python 3.14 may expose more unpinned or pinned packages without wheels (`cryptography==45.0.5`, `Werkzeug==3.1.1` and others were installed on 3.14 earlier, but only `psycopg2` was imported). Treat a 3.14 failure as a real finding: bump the pin in a separate PR with an issue, do not drop 3.14.
- `requests`, `openai>=1.0.0`, `langchain>=0.3.0`, `langchain-openai>=0.3.0` are unpinned, so a new upstream release can turn CI red without any change here. That is a signal about the template, not a flaky test; do not pin only to silence it without deciding that is the right fix.
- Install time is long because of `langchain`. Cache helps; acceptable.

## 8. Details decided at implementation time

Action versions (`actions/checkout`, `actions/setup-python`) looked up with `gh api` at that time; exact YAML; whether to add `pip check`.

## 9. Acceptance

- The workflow PR triggers the workflow itself, and `ci-ok` passes with both Python cells green.
- Reintroducing the old pin `psycopg2-binary==2.9.10` on a throwaway branch makes the 3.14 cell fail (try once, then close the PR).
- Reintroducing the stale import in `app/service/__init__.py` makes the import check fail.
- After the owner enables the ruleset, the merge button is disabled while `ci-ok` is red.
- The README says CI exists and shows the same commands to run locally.

## 10. Left to the builder

YAML layout, step wording, cache configuration, and whether `pip check` or a short startup smoke (`create_app("testing")` plus `GET /`) belongs in the `check` job.
